Claude Plays a Puzzle Game

In 2013, I wrote a puzzle game. I never really gave it a name, so let's call it Deadlock. In Deadlock, you use arrow keys (or WASD) to guide the Dude to the cupcake:

Arrows / WASD move  ·  R restart  ·  P/Q next/prev level  ·  Enter start

Port

I've been using Claude code to approach old problems I haven't thought about in years. Hopefully I'll be making more posts to discuss these. But for some reason, I remembered this little puzzle game, and I thought I would see what Claude was able to do with it.

The first step was to (prompt Claude to) port the game to Javascript. The original was in C++/SDL. The port was easy enough, the result is above. Please feel free to give the levels a shot!

Deadlock: JS port, automated solver, and a mechanic I missed

Deadlock is a small C++/SDL puzzle game: guide a little robot to a cupcake across 18 levels. I ported it to a single self-contained HTML file, then built a solver to answer a simple question: can it beat the levels? The answer is now 17 of 18, each in under 10 seconds. Getting there needed one hint-driven correction to how I understood the game.

The game is not really a maze

The walls are almost incidental. The puzzle is the moving blocks: every frame, each block moves in response to how you moved on the previous frame.

ColorTypesBehavior
Blue3, 4, 5moves with you (vertical, horizontal, both)
Green6, 7, 8moves opposite you (type 8 is a point mirror)
Red9, 10, 11moves perpendicular (your horizontal drives its vertical, and vice versa)

Blocks can't overlap walls, each other, or you. The usual trick is to ram a block into a wall so it gets stuck while you keep moving, which knocks it out of sync with you.

The miss: the cupcake

Level 10 has one green "point mirror" block. While neither of you is stuck, it conserves a quantity:

dudeX + blockX = constant
dudeY + blockY = constant

That pins your midpoint with the block to the center of the level's only one-tile-wide corridor, so you can never get past each other. My solver searched every reachable state and reported the level unsolvable. I responded by making the search finer and finer (2px stopping points, then diagonal movement), and none of it helped.

The user had to walk me in with three hints:

  1. "there's kind of a secret mechanic in level 10 that i don't think you're really getting"
  2. "what are ALL the types of tiles", which led me to the invariant (why it's hard) but not the way out
  3. "how do the moving blocks interact with the cupcake", which pointed straight at it

The original source treats the cupcake differently depending on who touches it:

if (tiles[t]->get_type() >= 1 && tiles[t]->get_type() < TILE_SPRITES) {
    if (isDude && tiles[t]->get_type() == 1) return false;              // you pass through
    else if (check_collision(box, tiles[t]->get_box())) return true;  // blocks are stopped
}

The cupcake is solid to blocks. It's the asymmetric wall you jam the mirror block against. My JS port had this right, but when I rewrote the physics for the solver I simplified block collision and dropped it. Adding one line solved level 10 in 0.2 seconds.

The lesson: when an exhaustive search says "impossible", that's a statement about your model, not the game. I should have audited the rules, not upgraded the search.

Iterating on the solver

Every variant ran all 18 levels in parallel with a 10-second cap per level. Every reported solution was replayed through the exact simulator to confirm it reaches the cupcake.

#ChangeSolvedNotes
0Python A*, stops every 2px near blocks7/18baseline
1Stop moves only on "events" (alignments, jams)3/18events fired too often; reverted
2Weighted A* (w = 2, 5)7/18no change
3Coarse tile-by-tile search, fine search as fallback11/18matches the old 120-second result
4Port the solver to Node, same logic17/18~100× faster; biggest single win
5Weighted A* on level 18 (up to w = 10)—no help: stuck, not wandering
6Novelty search: explore states with something new first17/18hard levels 5–10× faster
7Novelty over (dude, block) position pairs17/18no change on level 18

What the iterations showed:

  • Speed mattered most. The coarse model was already good enough; Python just couldn't run it fast enough. Frame counts match the Python solver exactly wherever both solved a level, which is good evidence the port has the same physics.
  • The fine 2px search was never needed. With the cupcake rule in, coarse search solves level 10 alone. My earlier precision work was compensating for the missing rule.
  • There's a speed/quality trade-off. Novelty search is fastest but finds longer solutions (level 9: 900 frames → 2,672). Plain A* still finds the shortest.

Why level 18 is still open

Level 18 ("Through a gauntlet") has 27 blocks, including a row of 15 red blocks that shift vertically on every sideways step. Mapping where the player gets to shows it reaches two cells from the cupcake but never enters column 19. A blue block there copies your vertical moves, and the neighboring columns span exactly the same rows, so ramming it into a wall can't separate you from it. The way through probably needs another block to wedge it in place: the green block beside it moves opposite to you and could slide into column 19. With so many blocks reshuffling on every move, the search drowns in near-identical states before finding that. Level 18 isn't shown to be unsolvable, only unsolved in 10 seconds by these approaches.

For the record, I had Claude up the timeout to 30 seconds, and it still was unable to solve level 18.
